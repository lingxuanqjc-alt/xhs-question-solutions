# 小红书问题帖解答

## 工作流

把小红书问题帖及评论转换为可追溯的解决方案。不要把点赞数、重复说法或亲历叙述直接当作事实。

1. 确认主题、时间范围和最多处理量。未指定时最多取 20 篇候选笔记，每篇最多取 100 条可见评论及其可见回复。
2. 按以下顺序获取数据：
   - 优先使用当前环境中可用的小红书专用 Agent、Skill 或连接器。
   - 笔记正文可复用 `$xhs` 的 Cookie + HTTP 获取方式；评论正文使用已登录浏览器读取公开可见内容。
   - 无法访问评论时，请用户提供平台导出的 JSON/JSONL；不要声称已分析未取得的评论。
   - 需要获取 URL 数据时读取 [references/acquisition.md](references/acquisition.md)。
3. 文件输入先保存原始数据，再运行 `python scripts/normalize_xhs_export.py <input.json|jsonl> <canonical.jsonl>`。少量内联文本先按数据契约提取为临时 JSON，在系统临时目录运行同一脚本，校验后清理临时文件；运行环境不允许时才做内存分析，并明确标注“未运行脚本校验”。
4. 读取 [references/evaluation-rubric.md](references/evaluation-rubric.md)，只让模型判断问题帖、分类评论并提取主张、条件、步骤和失败案例。每条评论选择一个主类别，兼具作用写入主张说明。
5. 先列共识，再表面化冲突。解决方案中的每一步必须引用至少一个评论 ID；无支持证据的内容只能放入“待验证”。
6. 按 [references/data-contract.md](references/data-contract.md) 生成 `analysis.json`，运行 `python scripts/validate_result.py <canonical.jsonl> <analysis.json>`。
7. 校验通过后输出中文 Markdown；失败时修正引用或降低结论，不要跳过校验。

## 输出顺序

1. **问题**：一句话复述发帖者真正要解决的事。
2. **可执行方案**：按先后顺序列步骤，每步附评论 ID 与适用条件。
3. **直接答案**：整理明确回答问题的评论。
4. **亲历经验**：分开列成功、失败和条件不明的经验。
5. **共识与冲突**：说明相互支持和相互矛盾的观点。
6. **风险与待验证**：列出猜测、样本偏差、缺失信息和高风险建议。
7. **证据索引**：保留评论 ID、匿名化作者、原文短摘、点赞数和回复关系。

## 约束

- 只处理公开内容或用户有权访问的数据；不绕过登录、风控或访问限制。
- 不调用未经现场验证的私有评论接口。浏览器不可用时明确降级为导出数据分析。
- 匿名化普通用户昵称；除非用户明确要求且有正当必要，不输出个人主页标识。
- 点赞数只描述关注度，不参与真假判定。
- 医疗、法律、金融和人身安全建议必须标记高风险，并建议用权威来源复核。
- 直接引用保持短小；综合结论必须能回溯到评论 ID。
